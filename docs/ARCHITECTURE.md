## 1. Принципы

- **Достоверность важнее скорости.** Ни одно уведомление не отправляется по единственной неудачной проверке.
- **Проверять то, что видит клиент.** Реестры блокировок и сторонние сервисы — справочная информация; состояние сервера определяют только собственные проверки.
- **Отсутствие данных — не отказ.** Если проверку нельзя выполнить достоверно (не работает DNS самого мониторинга, нет сети), результат — «нет вердикта», и он ничего не меняет.
- **Маршруты не смешиваются.** Прокси Telegram никогда не используется для проверок серверов.
- **Один процесс, один файл данных.** Никаких внешних баз, очередей и контейнеров.

## 3. Сетевые маршруты

| Направление | Маршрут | Чем задаётся |
|---|---|---|
| Telegram Bot API | через прокси | `TELEGRAM_PROXY_URL` или настройка из Telegram |
| Проверки серверов (DNS, TCP, QUIC, TLS, туннель) | напрямую | не настраивается |
| Cheburcheck | напрямую либо свой прокси | `CHEBURCHECK_PROXY_URL` |
| Загрузка подписок | напрямую либо свой прокси | `SUBSCRIPTION_PROXY_URL` |

Каждый HTTP-клиент создаётся со своим коннектором и с `trust_env=False`; переменные `HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY` удаляются из окружения при старте. Сквозная проверка идёт через локальный SOCKS-вход одноразового Xray-клиента на `127.0.0.1`, а сам Xray соединяется с сервером напрямую.

## 4. Подписки

### Загрузка

- Запрос выполняется с User-Agent `rw-monitor/1.0`. Панель Remnawave выбирает формат ответа по клиенту; для неизвестного клиента это список ссылок в base64.
- Дополнительно запрашиваются форматы по суффиксам пути (`/json`, `/mihomo`) — в них могут быть серверы и параметры, которых нет в ссылках. Списки объединяются.
- Если панель не отдаёт серверы незнакомому клиенту, при добавлении подписки перебираются User-Agent распространённых клиентов.
- Заголовки ответа используются для названия подписки, срока действия и диагностики лимита устройств.

### Лимит устройств (HWID)

Если панель требует идентификатор устройства, бот сообщает об этом и ждёт согласия владельца. Идентификатор создаётся один раз, хранится в базе и отправляется в заголовке `x-hwid`; его можно задать заранее параметром `SUBSCRIPTION_HWID`.

### Разбор

Формат определяется по содержимому, а не по заголовкам:

| Формат | Признак |
|---|---|
| Список ссылок | строки `vless://`, `trojan://`, `ss://`, `vmess://`, `hysteria2://`, в открытом виде или в base64 |
| Xray JSON | объект или массив объектов с `outbounds` |
| Mihomo / Clash | YAML с `proxies` |
| sing-box | JSON с `outbounds` и полем `type` |

Записи-заглушки, которыми панель сообщает об ошибке (адрес `0.0.0.0`, порт `1`, нулевой UUID), серверами не считаются; их текст показывается владельцу как сообщение панели.

### Идентификация сервера

- **Отпечаток** — хеш от адреса, порта, протокола, транспорта, типа защиты, SNI, заголовка Host и пути. Название и учётные данные в отпечаток не входят: смена UUID не создаёт новый сервер.
- **Узел** — адрес без порта и параметров. Несколько конфигураций одного узла отслеживаются раздельно, но уведомления по ним объединяются.
- Из нескольких записей с одним отпечатком остаётся одна; остальные названия сохраняются как псевдонимы. Название конфигурации-балансировщика («автовыбор») не вытесняет собственное название сервера.

### Сверка при обновлении

Новый список сопоставляется с сохранённым в три прохода: точный отпечаток → тот же адрес и порт с тем же названием (изменились SNI или путь) → те же порт, протокол, транспорт, защита и название при другом адресе (панель может выдавать разные адреса одного хоста). Несопоставленные записи добавляются, исчезнувшие серверы снимаются с наблюдения (история сохраняется).

Защитные правила:

- неудачный ответ или ответ из одних заглушек никогда не меняет список;
- если из ответа пропало больше половины серверов, изменение применяется только после подтверждения владельца;
- исключения и настройки сервера переживают обновление.

## 5. Проверка сервера

### Уровни

1. **DNS.** Системный резолвер; при отказе или сомнении — независимые резолверы (`DNS_RESOLVERS`). Отрицательный ответ (NXDOMAIN, нет записей) принимается, только если его подтвердили несколько резолверов. Если не отвечает ни один, уровень даёт «нет вердикта», а проверка продолжается по последним известным IP.
2. **TCP или QUIC.** Для TCP — соединение с каждым IP с повтором внутри проверки. Для UDP-протоколов — QUIC-пакет, на который сервер обязан ответить пакетом Version Negotiation; ICMP «порт недоступен» распознаётся как закрытый порт.
3. **TLS** (для `tls` и `reality`). Рукопожатие с SNI из конфигурации. Если в подписке задана фрагментация ClientHello, проба отправляет ClientHello такими же фрагментами. Запоминается отпечаток сертификата.
4. **Туннель.** Запускается отдельный процесс `xray` с одним выходом — проверяемым сервером — и локальным SOCKS-входом. Через него выполняется HTTP-запрос; периодически, а также при любых сомнениях, загружается 128 КБ.

### Сквозная проверка

- Если в подписке есть Xray JSON, используется исходная конфигурация выхода из панели; иначе она строится из параметров ссылки.
- Адрес в конфигурации заменяется на IP, прошедший нижние уровни, чтобы проверялся именно он.
- Конфигурация передаётся процессу через stdin: ключи не попадают ни на диск, ни в командную строку.
- Параметр «не проверять сертификат» в современных версиях Xray не поддерживается: вместо него закрепляется отпечаток сертификата, полученный TLS-пробой.
- Ошибка запуска или конфигурации Xray — это «проверка невозможна», а не отказ сервера.

### Вердикт

- Если сквозная проверка выполнена, её результат решающий. Нижние уровни показывают, на каком этапе отказ.
- Если нижние уровни уже отказали, через туннель делается одна контрольная попытка: упрощённая проба может не пройти там, где настоящий клиент работает.
- Без сквозной проверки (Xray не установлен, конфигурацию нельзя воспроизвести) вердикт выносят уровни 1–3. UDP-сервер с обфускацией в этом случае получает «нет вердикта».
- Сервер, у которого отвечает только часть адресов, считается доступным с пометкой «частично».

Каждому отказу соответствует код и текст причины: `dns_nxdomain`, `tcp_timeout`, `tcp_refused`, `tls_reset`, `tls_timeout`, `udp_no_reply`, `e2e_failed`, `e2e_timeout`, `e2e_stall` и другие.

## 6. Состояния и защита от ложных срабатываний

```
            неудача                N неудач подряд
   OK ───────────────► SUSPECT ───────────────────► DOWN ──┐
    ▲                     │                          ▲     │ M успехов подряд
    │       успех         │                неудача   │     ▼
    └─────────────────────┘        ┌─────────────────┴─ RECOVERED
    ▲                              │ (через SUSPECT)       │
    └──────────── период наблюдения истёк ─────────────────┘

   UNKNOWN — ещё не проверялся либо достоверного результата нет
```

Автомат состояний — чистая функция без ввода-вывода (`monitor/fsm.py`), полностью покрытая тестами.

| Мера | От чего защищает |
|---|---|
| Повтор внутри проверки (TCP, UDP, TLS) | единичная потеря пакета |
| N неудач подряд с паузами (по умолчанию 3; паузы 30 и 60 с) | кратковременный сбой маршрута, перезапуск сервиса |
| Паузы отсчитываются от окончания проверки | «слипание» наблюдений при долгом цикле |
| Наблюдения учитываются только с интервалом по времени | ускорение DOWN ручными проверками |
| M успехов подряд (по умолчанию 3) | ложное «восстановлен» |
| Самоконтроль до и после цикла | сбой сети самого мониторинга |
| «Нет вердикта» не меняет состояние | сбой DNS мониторинга |
| Массовый отказ → одно сводное сообщение | поток уведомлений |
| Нестабильный сервер (3 инцидента за час) → одно сообщение | серия падений и восстановлений |
| Туннель отказал на всех серверах подписки → перезапрос подписки | истёкшая или отключённая подписка |
| Уникальный ключ события | повтор уведомления, в том числе после перезапуска |

Проверка учётных данных работает так: если туннель не работает сразу на всех серверах подписки, а нижние уровни проходят, бот перезапрашивает подписку. Панель больше не выдаёт серверы — отправляется одно сообщение о проблеме подписки, сквозная проверка для неё приостанавливается. Панель подтверждает подписку — отказы настоящие. Панель недоступна — «нет вердикта».

## 7. Самоконтроль мониторинга

Перед каждым циклом и повторно, если в цикле есть отказы, проверяется собственная связь:

| Группа | По умолчанию | Вывод при отказе всей группы |
|---|---|---|
| Зарубежные узлы | `www.google.com:443`, `github.com:443`, `www.microsoft.com:443`, `8.8.8.8:53` | результаты цикла отбрасываются, состояния замораживаются |
| Российские узлы | `ya.ru:443`, `vk.com:443`, `77.88.8.8:53` | справочно: вместе с зарубежной группой — «нет связи с интернетом» |
| DNS | разрешение контрольного имени системным резолвером | отдельное предупреждение; проверки продолжаются через резервные резолверы |

Группа считается исправной, если отвечает хотя бы один её узел. Сообщение «Проблема мониторинга» отправляется, если проблема держится дольше минуты; после устранения приходит «Мониторинг восстановлен». Первый цикл после запуска начинается только после успешного самоконтроля.

## 8. Cheburcheck

[Cheburcheck](https://cheburcheck.ru) — сторонний сервис со статическими списками блокировок и сетью добровольческих сканеров у российских операторов. Используются два открытых метода его API:

| Метод | Данные |
|---|---|
| `GET /api/v1/check?target=` | статические: наличие в списках, подсети, диапазоны CDN, ASN, география |
| `GET /api/v1/probe/<id>` | динамические: поток результатов региональных сканеров |

API не документирован, поэтому разбор терпим к отсутствующим и новым полям, а систематическая ошибка разбора приводит к одному предупреждению владельцу.

### Что измеряют сканеры

Сканеры проверяют путь до 443-го порта за оборудованием DPI оператора, прохождение TLS с заданным SNI до контрольных хостов сервиса и ответы DNS. **Порт и протокол самого VPN-сервера они не проверяют.** Поэтому их данные — основание для предположения, а не вердикт.

| Вердикт сканера | Смысл | Свидетельство блокировки цели |
|---|---|---|
| `tspu_block` | пакеты к IP не проходят дальше DPI | да |
| `sni_block` | ClientHello с этим SNI остаётся без ответа | да |
| `dns_spoofing` | ответы обычного DNS расходятся с DoH/DoT | да |
| `whitelist` | SNI выведен из-под ограничения CDN «16–20 КБ» | нет |
| `cdn_block` | у оператора действует ограничение CDN, SNI из-под него не выведен — обычное состояние рядового имени | нет; значимо, только если IP сервера входит в диапазон CDN |
| `ok`, `uncertain` | блокировки не видно; неясно | — |

### Правила обращения

- Запросы выполняются только после подтверждённого DOWN и по кнопке в карточке сервера. При плановых проверках и в состоянии SUSPECT запросов нет.
- Запрашиваются IP сервера и его домен; локальные и служебные адреса не отправляются.
- Паузы между запросами с запасом к лимитам сервиса, суточный потолок, кеш результата (по умолчанию 1 час).
- После трёх ошибок подряд сервис считается недоступным: запросы прекращаются на 10–60 минут.
- Неполученные данные ждут в очереди в базе (до 6 попыток, не дольше суток). Когда данные получены, исходное уведомление дополняется.
- Недоступность сервиса не задерживает уведомление и не влияет на состояние сервера.

### Вероятная причина

Собственный результат сопоставляется с данными сканеров, и формулируется предположение — всегда с пометкой «вероятная причина». Например: таймаут TCP и блокировку видит большинство сканеров → «блокировка IP на ТСПУ»; таймаут TCP, сканеры блокировки не видят → «отказ сервера или сети хостера либо блокировка, специфичная для порта»; соединение отклонено → «сбой сервиса на сервере». Если замеров меньше трёх, вывод не делается.

## 9. Уведомления

- Источники событий только записывают сообщения в очередь в базе (`notifications`). Отдельная задача доставляет их в Telegram по порядку.
- При обрыве связи сообщение остаётся в очереди; повтор — не реже раза в минуту и сразу, как только связь подтверждена. Доставленное с опозданием сообщение содержит пометку о задержке и исходное время события.
- Один инцидент — одно сообщение о падении и одно о восстановлении. Конфигурации одного узла объединяются; при массовом отказе отправляется сводка.
- Сообщение о падении ждёт данные Cheburcheck ограниченное время (по умолчанию 40 секунд); если данные пришли позже, сообщение редактируется.
- Некорректная разметка не приводит к потере сообщения: оно отправляется простым текстом.

Доступ: внешний фильтр диспетчера пропускает только обновления от `TELEGRAM_OWNER_ID` из личного чата. Остальные отбрасываются без ответа; в журнал попадает только счётчик.

## 10. Хранение данных

SQLite в режиме WAL. Версия схемы хранится в `PRAGMA user_version`, миграции применяются при запуске.

| Таблица | Содержимое |
|---|---|
| `settings` | настройки, изменённые из Telegram, и служебные значения |
| `subscriptions` | подписки: зашифрованная ссылка, состояние, срок действия |
| `servers`, `server_addresses`, `server_subscriptions` | серверы, их адреса и связи с подписками |
| `server_state` | текущее состояние и счётчики |
| `checks` | история проверок (ограниченный срок хранения) |
| `incidents`, `state_events` | инциденты и смены состояний |
| `notifications` | очередь и история сообщений |
| `cheburcheck_results`, `cheburcheck_queue` | результаты и отложенные запросы |
| `monitor_events` | события мониторинга и действия владельца |

Секреты:

- ссылки подписок, учётные данные серверов и адрес прокси, заданный из Telegram, шифруются ключом `SECRET_KEY`; резервная копия без ключа их не раскрывает;
- фильтр журнала маскирует токен бота, ссылки подписок, учётные данные прокси, UUID и содержимое ссылок на серверы.

Обслуживание: раз в час удаляется история старше заданного срока (открытые инциденты и неотправленные сообщения не удаляются никогда); раз в сутки создаётся резервная копия средствами SQLite, лишние копии удаляются.

## 11. Жизненный цикл процесса

- Служба systemd типа `notify`: готовность сообщается после запуска мониторинга; сторожевой таймер получает сигнал, только пока цикл мониторинга продвигается.
- Блокировка каталога данных не даёт запустить второй экземпляр.
- Раз в 30 секунд записывается отметка «жив». По ней при запуске вычисляется простой; после долгого простоя счётчики начинаются заново: подтверждённый DOWN остаётся DOWN, неподтверждённое подозрение сбрасывается.
- Недоступность Telegram не останавливает мониторинг: опрос Bot API и доставка повторяются с нарастающей паузой.
- Прокси, заданный из Telegram и переставший работать, автоматически заменяется значением из файла конфигурации.
- Код завершения 2 означает ошибку конфигурации: systemd в этом случае службу не перезапускает.

Установка построена на каталогах версий: `/opt/rw-monitor/releases/<дата>` и ссылка `/opt/rw-monitor/current`. Обновление собирает новую версию рядом с работающей, делает копию базы, переключает ссылку и при неудачном запуске возвращает прежнюю версию.
