# rw-monitor

**Telegram-бот, который следит за доступностью серверов из подписок [Remnawave](https://github.com/remnawave) из российской сети и сообщает о подтверждённых падениях и восстановлениях.**

![status](https://img.shields.io/badge/status-beta-orange)
![python](https://img.shields.io/badge/python-3.11%2B-blue)
![license](https://img.shields.io/badge/license-MIT-green)

> [!WARNING]
> **Проект находится в стадии BETA.**
>
> - Это ранняя бета-версия: возможны ошибки, поведение и формат настроек могут измениться.
> - Использовать в production без предварительного тестирования на своей инфраструктуре **не рекомендуется**.
> - Часть сценариев проверена только на стенде — что именно проверено и что нет, честно перечислено в [docs/TESTING.md](docs/TESTING.md) и в разделе [«Известные ограничения»](#известные-ограничения-и-проблемы).
> - Сообщения об ошибках и предложения приветствуются: [Issues](https://github.com/Rrezzak09VPN/rw-monitor/issues).

Бот ставится на отдельный VPS в России, берёт список серверов из обычной **клиентской** подписки и проверяет каждый сервер так, как это сделал бы VPN-клиент. Главный принцип — достоверность: лучше сообщить на минуту-две позже, чем поднять ложную тревогу.

## Возможности

**Источник серверов — клиентская подписка**

- Достаточно прислать боту ссылку на подписку. К административному API панели бот не подключается.
- Форматы определяются по содержимому: список ссылок (base64 и открытый), Xray JSON, Mihomo/Clash YAML, sing-box JSON.
- Протоколы: VLESS, Trojan, Shadowsocks, Hysteria2 (в ссылках также VMess).
- Одинаковые записи схлопываются; несколько конфигураций одного сервера отслеживаются отдельно, но при одновременном падении дают одно уведомление.
- Повторная отправка ссылки и автообновление: новые серверы добавляются, исчезнувшие снимаются с наблюдения, исключения и история сохраняются.
- Панели с лимитом устройств (HWID): бот объясняет ситуацию и отправляет идентификатор устройства только после явного согласия.
- Неудачное обновление (ошибка сети, истёкшая подписка, «заглушки» вместо серверов) никогда не меняет список серверов.

**Проверка доступности**

- Четыре уровня: DNS → TCP/QUIC → TLS → запрос через настоящий Xray-клиент с данными подписки.
- Открытый порт не считается признаком работающего VPN: итог определяет сквозная проверка, нижние уровни показывают, где именно отказ.
- Периодическая загрузка 128 КБ через туннель ловит обрыв после 16–20 КБ.
- Проверки всегда идут напрямую с сервера мониторинга — без VPN и прокси.

**Защита от ложных срабатываний**

- Состояния OK → SUSPECT → DOWN → RECOVERED, отдельно UNKNOWN.
- DOWN — только после N неудач подряд с паузами, RECOVERED — после M успехов подряд; все пороги и интервалы настраиваются.
- Самоконтроль: если у самого мониторинга нет сети, результаты отбрасываются, а владелец получает одно сообщение «Проблема мониторинга».
- Сбой DNS на сервере мониторинга даёт «нет вердикта», а не падение.
- Массовый отказ — одно сводное сообщение; нестабильный сервер — одно предупреждение вместо серии.
- Истёкшая подписка не выдаётся за падение всех серверов.

**Cheburcheck**

- Запрашивается только после подтверждённого падения или по кнопке — для IP и домена сервера.
- Замеры региональных сканеров и наличие в списках показываются раздельно, со статусом достоверности данных.
- Если сервис недоступен, уведомление не задерживается, сервер не помечается заблокированным, данные досылаются позже.

**Telegram**

- Один владелец: сообщения и нажатия кнопок от других пользователей игнорируются полностью.
- Bot API через отдельный прокси (проверено с SOCKS5; схема `http://` принимается, но не тестировалась); смена прокси из Telegram с проверкой перед применением.
- Инлайн-меню: статус, список серверов, подписки, настройки, исключения, история, ручная проверка.
- Исключения: полное, пауза на время, отключение только уведомлений.
- Очередь уведомлений переживает обрыв связи и перезапуск.

**Эксплуатация**

- Один процесс и один файл SQLite; служба systemd с автозапуском и сторожевым таймером.
- Состояния, счётчики, настройки и очередь сообщений сохраняются между перезапусками.
- Ежедневные резервные копии, ограничение срока хранения истории.
- Секреты зашифрованы в базе и замаскированы в журнале.

> Что из этого проверено на реальных серверах, а что только на стенде — см. [docs/TESTING.md](docs/TESTING.md).

## Как это работает

```
              подписка Remnawave (клиентская ссылка)
                           │  напрямую
                           ▼
┌──────────────────────── rw-monitor ────────────────────────┐
│  разбор форматов → список серверов → планировщик           │
│                                         │                  │
│   DNS → TCP/QUIC → TLS → туннель (Xray) ┘   самоконтроль   │
│                │                                           │
│        автомат состояний → инциденты → очередь сообщений   │
└───────┬─────────────────────┬──────────────────┬───────────┘
        │ напрямую            │ напрямую         │ через прокси
        ▼                     ▼                  ▼
   VPN-серверы           Cheburcheck        Telegram Bot API
```

| Уровень | Что делается | Что выявляет |
|---|---|---|
| 1. DNS | системный резолвер, при сомнении — независимые | удалённый домен; отказ засчитывается, только если его подтвердили несколько резолверов |
| 2. TCP / QUIC | соединение с каждым IP (с повтором); для UDP-протоколов — QUIC-проба | недоступный хост, закрытый порт, блокировку IP |
| 3. TLS | рукопожатие с SNI из конфигурации, с той же фрагментацией ClientHello, что задана в подписке | сброс или молчание после ClientHello, «ложно открытый» порт |
| 4. Туннель | Xray-клиент с данными подписки, HTTP-запрос через сервер | блокировку протокола, обрыв после 16–20 КБ, неработающий сервис при открытом порте |

При значениях по умолчанию DOWN объявляется примерно через 1,5–2 минуты после первой неудачи. Подробности — в [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

## Требования

| | |
|---|---|
| ОС | **Ubuntu 24.04 LTS** — единственная система, на которой проверялся установщик |
| Архитектура | x86_64 (проверено); aarch64 поддерживается установщиком, но не тестировалась |
| Права | root (или пользователь с `sudo`) |
| Система инициализации | systemd — сервис устанавливается как служба |
| ПО | Python ≥ 3.11 (в Ubuntu 24.04 — 3.12). Python, `venv`, `curl`, `unzip` установщик ставит сам |
| Память | около 200 МБ занимает сам сервис; рекомендуется VPS с 1 ГБ ОЗУ |
| Диск | ~300 МБ под программу и зависимости; база на 15 серверов — 10–15 МБ |
| Сеть | прямой выход в интернет; на время установки — доступ к github.com и pypi.org |
| Telegram | токен бота от [@BotFather](https://t.me/BotFather) и ваш числовой ID (подскажет [@userinfobot](https://t.me/userinfobot)); если Bot API недоступен напрямую — рабочий прокси (проверено с SOCKS5) |

Docker, внешние базы данных и очереди не нужны. Xray-core (отдельная программа, лицензия MPL-2.0) скачивается установщиком из официальных релизов, версия закреплена, контрольная сумма проверяется.

## Быстрая установка

На чистой Ubuntu 24.04:

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/Rrezzak09VPN/rw-monitor/beta/install.sh)
```

Если `curl` не установлен: `apt-get update && apt-get install -y curl`.
Команду можно запускать от root или от пользователя с `sudo` — установщик сам запросит повышение прав.

Установщик:

1. проверяет систему (ОС, архитектуру, наличие systemd);
2. ставит системные пакеты: `python3`, `python3-venv`, `curl`, `unzip`, `ca-certificates`;
3. создаёт системного пользователя `rwmon` без права входа;
4. размещает программу в `/opt/rw-monitor` (отдельное окружение Python, зависимости закреплённых версий);
5. скачивает Xray-core в `/opt/rw-monitor/bin/xray` и сверяет SHA-256;
6. создаёт `/etc/rw-monitor/rwmon.env` из [.env.example](.env.example) и генерирует ключ шифрования;
7. спрашивает обязательные параметры — токен бота (ввод скрыт), ваш Telegram ID и, при необходимости, прокси для Telegram;
8. регистрирует службу systemd `rw-monitor` с автозапуском;
9. выполняет самопроверку (сеть, DNS, Xray, Telegram, Cheburcheck), запускает службу и показывает её состояние;
10. печатает итог: версию, пути к конфигурации и данным, дальнейшие шаги.

Установка без вопросов (например, из скрипта):

```bash
TELEGRAM_BOT_TOKEN='123456789:AA…' TELEGRAM_OWNER_ID=123456789 \
TELEGRAM_PROXY_URL='socks5://user:pass@203.0.113.5:1080' RWMON_NONINTERACTIVE=1 \
bash <(curl -fsSL https://raw.githubusercontent.com/Rrezzak09VPN/rw-monitor/beta/install.sh)
```

Если обязательные параметры не заданы и спросить их негде, установка завершается без запуска службы и подсказывает, что заполнить.

<details>
<summary>Дополнительные параметры установщика</summary>

| Переменная | Назначение |
|---|---|
| `RWMON_NONINTERACTIVE=1` | ничего не спрашивать |
| `XRAY_ZIP=/путь/Xray-linux-64.zip` | взять заранее скачанный архив Xray (если github.com с сервера недоступен) |
| `XRAY_VERSION=v26.11.9` | другая версия Xray-core |
| `RWMON_SKIP_XRAY=1` | не ставить Xray: останутся уровни DNS → TCP/QUIC → TLS |
| `RWMON_NO_START=1` | не запускать службу после установки |
| `RWMON_ALLOW_UNSUPPORTED_OS=1` | продолжить на другой системе с apt и systemd (не тестировалось) |
| `RWMON_BRANCH`, `RWMON_REPO` | другая ветка или форк |

Установка из локальной копии репозитория: `sudo bash install.sh`.

</details>

## Первоначальная настройка

1. **Создайте бота** у [@BotFather](https://t.me/BotFather) (`/newbot`) и узнайте свой числовой ID у [@userinfobot](https://t.me/userinfobot).
2. **Запустите установщик** и ответьте на его вопросы.
   Если сервер находится в России и Bot API напрямую недоступен, укажите прокси для Telegram. Он используется только для Bot API.
3. **Проверьте самопроверку** в выводе установщика (в любой момент её можно повторить: `sudo rwmon selftest`):

   ```
   [OK  ] Связь с зарубежными контрольными узлами (напрямую): зарубежные узлы: 4/4
   [OK  ] Связь с российскими контрольными узлами (напрямую): российские узлы: 3/3
   [OK  ] Системный DNS: DNS: ок
   [OK  ] Xray-core для сквозной проверки: Xray 26.11.9
   [OK  ] Telegram Bot API (socks5://***@203.0.113.5:1080): @my_bot
   [OK  ] Cheburcheck: отвечает
   ```

4. **Откройте чат с ботом** и отправьте `/start`. Должно прийти сообщение «Мониторинг запущен» и меню.
5. **Пришлите ссылку на подписку.** Бот скачает её, покажет отчёт об импорте и начнёт проверки. Сообщение со ссылкой бот удалит из чата.
6. При желании измените интервал и пороги: «⚙️ Настройки мониторинга».

Если что-то пошло не так: `journalctl -u rw-monitor -n 50` и раздел [«Если бот не отвечает»](#если-бот-не-отвечает).

## Конфигурация

Единственный файл — `/etc/rw-monitor/rwmon.env`. Все параметры с пояснениями перечислены в [.env.example](.env.example).

Обязательны три:

| Параметр | Значение |
|---|---|
| `TELEGRAM_BOT_TOKEN` | токен бота |
| `TELEGRAM_OWNER_ID` | числовой ID единственного владельца |
| `SECRET_KEY` | ключ шифрования данных в базе (создаёт установщик; сохраните копию) |

После правки файла: `sudo systemctl restart rw-monitor`. Проверить файл без перезапуска: `sudo rwmon check-config`.

### Сетевые маршруты

Маршруты независимы и никогда не смешиваются:

| Что | Как идёт | Параметр |
|---|---|---|
| Telegram Bot API | через прокси | `TELEGRAM_PROXY_URL` |
| Проверки серверов | **всегда напрямую** | — (прокси не предусмотрен) |
| Cheburcheck | напрямую или через свой прокси | `CHEBURCHECK_PROXY_URL` |
| Загрузка подписок | напрямую или через свой прокси | `SUBSCRIPTION_PROXY_URL` |

Переменные окружения `HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY` при старте удаляются из процесса, чтобы случайно унаследованный прокси не повлиял на проверки.

### Что можно менять из Telegram

Интервал цикла, пороги, интервалы перепроверок, таймауты, параллелизм, параметры Cheburcheck, сквозную проверку, автообновление подписок, прокси Telegram, общую паузу. Значение, заданное в Telegram, хранится в базе, переживает перезапуск и имеет приоритет над файлом; кнопка «Вернуть значение из конфигурации» отменяет его.

## Работа с ботом

Бот отвечает только владельцу и только в личном чате. Интерфейс — на русском языке.

| Кнопка | Что делает |
|---|---|
| 📊 Статус мониторинга | серверы по состояниям, последний цикл, самоконтроль, Cheburcheck, маршруты |
| 🖥 Список серверов | название, адрес, состояние, время и результат последней проверки; фильтры |
| ➕ Добавить подписку | добавление, обновление, автообновление, удаление подписок |
| ⚙️ Настройки мониторинга | настраиваемые параметры, общая пауза, резервная копия |
| 🔕 Управление исключениями | исключённые, приостановленные и «заглушённые» серверы |
| 📋 История событий | смены состояний, проблемы мониторинга, события подписок |
| 🔄 Проверить все серверы | внеочередная проверка с итоговой сводкой |

Команды: `/menu`, `/status`, `/cancel`, `/help`.

Карточка сервера: 🔄 проверить сейчас · ⏯ включить / отключить мониторинг · 🔕 исключения · ℹ️ подробности · 📈 история доступности · 🔍 Cheburcheck.

| Исключение | Проверки | Уведомления |
|---|---|---|
| Исключить полностью | нет | нет |
| Пауза на 1 ч / 6 ч / 24 ч / свой срок | нет, возобновятся сами | нет |
| Отключить уведомления | **да** | нет |

| Состояние | Смысл |
|---|---|
| 🟢 OK | доступен |
| 🟡 SUSPECT | была неудача, идут быстрые перепроверки — уведомлений нет |
| 🔴 DOWN | недоступность подтверждена — одно уведомление |
| 🟢 RECOVERED | восстановление подтверждено — одно уведомление, далее период наблюдения |
| ⚪️ UNKNOWN | достоверного результата нет |

Пример уведомления:

```
🚨 СЕРВЕР НЕДОСТУПЕН

Сервер: 🇩🇪 Германия
Домен: node.example.com
IP: 203.0.113.10
Порт: 443 · VLESS · TCP · REALITY
Состояние: DOWN
Обнаружено: 12:34:56 МСК (подтверждено 3 проверками к 12:36:26 МСК)
Причина: нет ответа на TCP-соединение (таймаут)

Вероятная причина: блокировка IP на ТСПУ (её видят 31 из 36 сканеров…)

Cheburcheck
🔎 IP 203.0.113.10 — ✅ данные получены
Замеры у операторов (ответили 39 из 40 сканеров):
• Блокировка на ТСПУ: 31 — Москва (Beeline, Rostelecom), …
• Блокировки не видно: 5
Наличие в списках (справочно, это не замер):
• Списки блокировок: нет · Подсети РКН: нет
```

## Обновление

Повторите команду установки:

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/Rrezzak09VPN/rw-monitor/beta/install.sh)
```

Что происходит при обновлении:

- новая версия полностью собирается рядом с работающей — сервис в это время продолжает работать;
- **файл конфигурации не изменяется**, база данных сохраняется;
- перед переключением создаётся резервная копия базы (`/var/lib/rw-monitor/backups/pre-update-….sqlite3`);
- если новая версия не запустилась, установщик возвращает прежнюю версию и прежнюю базу и сообщает об ошибке;
- схема базы при необходимости обновляется автоматически при запуске;
- предыдущая версия программы остаётся в `/opt/rw-monitor/releases` до следующего обновления.

Перед обновлением загляните в [CHANGELOG.md](CHANGELOG.md): пока проект в бете, между версиями возможны несовместимые изменения.

## Удаление

Удалить сервис и программу, сохранив настройки и данные:

```bash
sudo bash /opt/rw-monitor/uninstall.sh
```

Удалить всё, включая конфигурацию, базу, резервные копии и служебного пользователя:

```bash
sudo bash /opt/rw-monitor/uninstall.sh --purge
```

Если программа уже удалена, а данные остались:

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/Rrezzak09VPN/rw-monitor/beta/uninstall.sh) --purge
```

После удаления не забудьте удалить устройство мониторинга в панели Remnawave, если подписка добавлялась с идентификатором устройства (HWID).

## Обслуживание

```bash
sudo systemctl status rw-monitor         # состояние службы
sudo systemctl restart rw-monitor        # перезапуск
journalctl -u rw-monitor -f              # журнал в реальном времени

sudo rwmon check-config                  # проверить файл конфигурации
sudo rwmon selftest                      # сеть, DNS, Xray, Telegram, Cheburcheck
sudo rwmon backup                        # резервная копия базы (можно при работающем сервисе)
sudo rwmon restore <файл>                # восстановление (сервис должен быть остановлен)
sudo rwmon reset-proxy                   # вернуть прокси Telegram из файла конфигурации
```

### Расположение файлов

| Путь | Содержимое |
|---|---|
| `/etc/rw-monitor/rwmon.env` | конфигурация (доступ: root и служебный пользователь) |
| `/var/lib/rw-monitor/rwmon.sqlite3` | база данных |
| `/var/lib/rw-monitor/backups/` | резервные копии |
| `/opt/rw-monitor/current` | текущая версия программы (ссылка на каталог в `releases/`) |
| `/opt/rw-monitor/bin/xray` | Xray-core для сквозной проверки |
| `/etc/systemd/system/rw-monitor.service` | служба systemd |

### Резервное копирование

- Ежедневно (по умолчанию в 04:00 МСК) создаётся копия базы, хранятся последние 7.
- Вручную: кнопка «💾 Резервная копия» в настройках или `sudo rwmon backup --out /путь/файл.sqlite3`.
- Для восстановления на другом сервере нужны **файл базы и `SECRET_KEY`** из `rwmon.env`: без ключа ссылки подписок и учётные данные серверов не расшифровать.

```bash
sudo systemctl stop rw-monitor
sudo rwmon restore /var/lib/rw-monitor/backups/rwmon-20261110-040000.sqlite3
sudo systemctl start rw-monitor
```

### Если бот не отвечает

1. `sudo systemctl status rw-monitor` и `journalctl -u rw-monitor -n 50` — работает ли служба.
2. `sudo rwmon selftest` — доступен ли Telegram через прокси, принят ли токен.
3. Прокси был изменён из Telegram и перестал работать — бот сам вернётся к значению из файла конфигурации после нескольких неудачных проверок. Принудительно: `sudo rwmon reset-proxy && sudo systemctl restart rw-monitor`.
4. Вы пишете боту с того аккаунта, чей ID указан в `TELEGRAM_OWNER_ID`? Остальным бот не отвечает.

Чтобы узнать о полном отказе самого сервера мониторинга, задайте `HEARTBEAT_URL` (например, адрес проверки healthchecks.io): пока мониторинг работает, адрес регулярно запрашивается.

## Безопасность

- Сервис работает от непривилегированного пользователя в изолированном окружении systemd; доступ на запись — только к своему каталогу данных.
- Файл конфигурации доступен только root и служебному пользователю; база и резервные копии — только служебному пользователю.
- Ссылки подписок, ключи и пароли серверов, адрес прокси, заданный из Telegram, хранятся в базе в зашифрованном виде.
- В журнал не попадают токен бота, полные ссылки подписок, UUID, пароли и учётные данные прокси. Ссылка подписки отображается как `host/…XXXX`.
- Сообщения со ссылкой на подписку и с адресом прокси бот удаляет из чата.
- Конфигурация одноразового Xray-клиента передаётся ему через stdin и не попадает ни на диск, ни в список процессов.

Нашли уязвимость — пожалуйста, не публикуйте подробности в открытом issue; порядок описан в [CONTRIBUTING.md](CONTRIBUTING.md#уязвимости).

## Известные ограничения и проблемы

**Статус проверки (бета)**

- Все автотесты и живые прогоны выполнялись в песочнице **за пределами России**. Поведение при реальной блокировке ТСПУ воспроизводилось только по её сетевым признакам (таймаут, сброс после ClientHello, обрыв после 16 КБ).
- На реальных серверах проверена одна подписка с конфигурациями VLESS · TCP · REALITY. Trojan, Shadowsocks, WebSocket и Hysteria2 проверены на локальном стенде с настоящим Xray. **XHTTP, gRPC, HTTPUpgrade и mKCP в сквозной проверке не испытывались.**
- Установщик проверен в окружении Ubuntu 24.04 с заменителем systemd; запуск службы настоящим systemd и поведение после перезагрузки сервера нужно проверить на своём VPS.
- IPv6-серверы и архитектура aarch64 не тестировались.
- Длительная работа (сутки и более) не проверялась.

**Особенности работы**

- Точка наблюдения — дата-центр. Фильтрация у домашних и мобильных операторов может отличаться; «белые списки» мобильного интернета из ЦОД не видны.
- Сквозная проверка использует данные подписки: бот действует как ещё один клиент, расходует немного трафика и занимает место в лимите устройств, если он включён.
- Источник серверов — только клиентская подписка: узлы, не выдаваемые этому клиенту, бот не увидит.
- Причина отказа — всегда предположение («вероятная причина»): отличить блокировку от аварии со стороны достоверно нельзя.
- API Cheburcheck не документирован и может измениться. На сам мониторинг это не влияет.
- UDP-протокол с обфускацией без установленного Xray достоверно проверить нельзя — состояние показывается как UNKNOWN.
- Бот не сообщит о собственной гибели: для этого служат сторожевой таймер systemd и необязательный `HEARTBEAT_URL`.
- Потребление памяти около 200 МБ.
- Один владелец, интерфейс только на русском языке, образа Docker нет.

Список известных проблем ведётся в [Issues](https://github.com/Rrezzak09VPN/rw-monitor/issues).

## Разработка и тесты

```bash
git clone -b beta https://github.com/Rrezzak09VPN/rw-monitor.git && cd rw-monitor
python3 -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt pytest pytest-asyncio && pip install -e .

XRAY_BIN=/путь/к/xray pytest             # все тесты, около 4 минут
pytest -m "not network"                  # без обращений в интернет
```

Интеграционные тесты поднимают на loopback настоящие серверы Xray и заменители панели Remnawave, Telegram Bot API, Cheburcheck и SOCKS5-прокси. Без бинарника Xray эти тесты пропускаются.

```
rwmon/
  config.py, settings.py      конфигурация из .env и настройки из Telegram
  security.py, logging_setup.py   шифрование секретов, маскирование в журнале
  db/                         SQLite: схема, миграции, доступ
  subscription/               загрузка подписок, разбор форматов, сверка списка серверов
  checks/                     DNS, TCP/QUIC, TLS, сквозная проверка, самоконтроль
  monitor/                    планировщик, автомат состояний, инциденты, уведомления
  cheburcheck/                клиент, очередь, кеш, предохранитель, сводки
  telegram/                   бот, доступ, экраны, обработчики, доставка сообщений
  maintenance.py              хранение истории, резервные копии
  app.py, __main__.py         сборка приложения, командная строка
deploy/                       служба systemd
tests/                        модульные и интеграционные тесты, заменители внешних сервисов
docs/                         архитектура, тестирование
install.sh, uninstall.sh      установка, обновление, удаление
```

Документация: [архитектура](docs/ARCHITECTURE.md) · [тестирование](docs/TESTING.md) · [история изменений](CHANGELOG.md).
